# 行程规划

完整或精简攻略在检索之前读。冲突时，本节覆盖「每天必须 2–4 个锚点」这类数量口诀。

本节是**收集问卷、缺省值、锁定项、改需求重算范围、减负顺序**的唯一出处；SKILL.md 只指向这里，不重复。

用户说了车型、能源、预算数字、孩子年龄时，那些事实覆盖本节默认。本节默认值只在用户没说时生效。

## 开口不够时：先问一轮

用户只说「帮我规划 / 做攻略 / 周末去哪 / 我想出去玩」，而目的地、日期或天数、怎么走、人数里缺了大半：发下面这段，然后**停住等他们填**。不要边问边搜，也不要先交一份默认行程。

可以按对方语气微调，但必须**一次问完**，不要拆成多轮。不确定的让他们写「看着办」。这里的公共交通是飞机 / 高铁 / 火车，不是市内公交。不要问钥匙或订票账号。

> 好，我来帮你排。把能确定的填一下，不确定的写「看着办」，填完我直接出行程。
>
> 1. 去哪（必填。还没想好就说想轻松还是想玩、大概几天，我给你 2–3 个地方选）
> 2. 从哪出发
> 3. 哪天走、玩几天（或「国庆 / 周末」）
> 4. 几个人；有没有小孩或老人
> 5. 怎么走：自驾 / 高铁 / 飞机 / 火车 / 混合
> 6. 预算：人均或总预算，或者经济 / 舒适 / 豪华
> 7. 节奏：轻松 / 适中 / 赶
> 8. 必须去、不要去、已订酒店或航班、不能吃的、不爬山（没有就空着）
> 9. 要不要一份能点开的网页攻略

**开口已经够用就不要再盘问。** 已经有目的地 +（日期或天数）+ 怎么走：其余按下表默认补上并写明假设，直接规划。用户说「看着办 / 你定 / 随便」的字段用默认，不要再追问。

| 字段 | 缺了怎么办 |
|---|---|
| 目的地 | 唯一硬阻塞。若问「五一去哪 / 帮我选」，给 2–3 个目的地（季节、花费、车程）等他们选；若说「帮我定一个」则直接定 |
| 日期 / 天数 | 从「周末 / 三天两夜 / 国庆」推断；否则默认 3 个完整日并写明 |
| 同行人 | 默认 2 位成人；这只用于演算和规划，不得写成用户已确认的信息。尊重亲子 / 带老人 / 独自 / 朋友 |
| 预算 | 默认舒适但不奢侈。只有用户给了数字上限，才当设计约束 |
| 节奏 | 默认适中。负荷规则见本文件下文，不要为了凑「每天 2–4 个点」再加景点 |
| 兴趣 | 能推断就推断；否则经典景点 + 一个本地街区 |
| 出发地 + 大交通 | 两个字段一起看：出发地用来排大交通，没有就不要编城际票。方式为高铁 / 飞机 / 自驾 / 混合；说不清时，不会改变行程结构就选最明显方案并写明，会明显改变天数、城市顺序或预算就给 2 个主方案，不强猜 |
| 车型 / 能源 | 没说就按普通轿车。限高、充电、增程只在用户说了才筛 |
| 自驾进城限制 | 先按**出行当月**官方公告查限行 / 尾号 / 预约通行，再排骨架；盖住行程时段就改交通或改过夜点。规则见 [china.md](china.md) |
| 限制 | 尊重饮食、儿童年龄、行动不便、不爬山、停车、早班机 |

## 锁定项

用户已确认的酒店、路线、出发时刻、预算上限视为锁定，后面检索到「更好的」也不能偷偷换。只有用户要求更换、已关闭/无法入住、或明显违反硬约束（无障碍、饮食、车位）时才解锁。

- 已定酒店：当主住，最多再给 1 个备选，除非他们要换。
- 已定路线：只改冲突点（闭馆、车程、天气、停航），不要重排全程。
- 只要改某一天 / 只要吃 / 只要打包 / 只要润色：不要整份重做，也不要重新检索无关项目。

## 用户中途改需求：按范围重算

不要一律全部重来：

| 变更 | 要重算 | 可以复用缓存 |
|---|---|---|
| 加 / 减一天 | 行程骨架、受影响那几天的片区划分、住宿晚数、预算 | 已核实的店和票；未受影响的整天 |
| 换目的地 / 换城 | 全部骨架 + 全部检索（新地方没有可用缓存） | 出发地到大交通方式、同行人约束、打包逻辑 |
| 改人数 / 同行类型（加孩子、加老人） | 住宿房型、负荷、备选强度、餐饮选择 | 景点和车次的真实存在性 |
| 改日期 / 改季节 | 高时效事实（票价、开放时间、天气、假期）、住宿价格带 | 店名、景点介绍、片区特点 |
| 改交通方式（自驾↔高铁↔飞机） | 大交通、市内移动、停靠表、`htmlMode` 和相关地图结构 | 住宿（除非车位变成筛选条件）、景点、餐饮 |
| 改预算上限 | 住宿档位、餐饮档位、可选门票、升级项 | 行程结构（只要不因钱改天数） |
| 加一天只玩 / 只想吃 / 只要打包 | 只有那一节 | 其余全部 |

改完要说明**动了哪些**、**哪些沿用上次**。涉及高时效事实的重算，按 [research-playbook.md](research-playbook.md) 的「缓存何时作废」判断。

## 用户说「太满了 / 走不完 / 想轻松点」

按这个顺序减，不要整份重排：

1. 先砍「顺路性最差」的那个锚点（要专门绕路的）
2. 再砍可替代性最高的（同类景点里的第二个、网红打卡点）
3. 把大块时间还给缓冲和用餐，不要用「加快一点」消化
4. 每天保留一个「这天最值得的」锚点作为骨架，其余都可删
5. 减完给一句说明：砍了哪几个、为什么、还剩下什么

只减不加。用户说轻松就不要再补「如果还有时间可以…」。真减不下来（硬时刻 + 硬预算同时卡死）就直说，给换天数或换片区的选项。

## 先骨架

先定过夜城市、每天主题/片区、交通方式和负荷，再去搜店和票。不要先搜十家店再倒推路线。

内部记住即可，不要输出给用户：目的地、日期、同行、预算、交通、兴趣、限制、锁定项、每天片区、检索缓存、时间/预算是否说得通。
默认人数只用于演算和规划，不得写成用户已确认的信息。

## 锁定项

用户已确认的酒店、路线、出发时刻、预算上限视为锁定。后续检索到评分更高的店，也不能偷偷换掉。

只有这些情况才解锁：用户要求更换；已关闭或无法入住；明显违反用户硬约束（无障碍、饮食、车位）。

## 地理聚类

同片区尽量安排在同一天。不要折返拉锯。不要为了午饭跨城。
用户没允许途经 / 环线，就不要加额外城市。环线会把天数撑爆时，说明原因并给更紧的主线。
第一次去：经典 + 一个本地街区。回头客：除非要求，否则跳过最热门点。

## 负荷，不是凑点数

锚点数量是结果，不是规划目标。不要因为「今天只有两个景点」再塞一个。

| 日型 | 典型负荷 |
|---|---|
| 普通城市日 | 2–4 个锚点 |
| 大型博物馆 / 古城慢逛 | 1–2 个 |
| 主题乐园 / 登山 / 海岛海滩日 | 1 个主项目即满日 |
| 长途自驾（车程约 ≥ 5 小时） | 0–2 个；开车本身是当天 |
| 抵达日 / 离开日 | 按半天 |

时间预算要算进：游玩 + 步行 + 车程 + 停车 + 排队 + 吃饭 + 缓冲。热门分时可以占满一天。超过 2 天的行程，每天留一段休息。必须预订的事项放最前面。

**可用时长 ≠ 行程时长**：10:00–20:00 不是 10 小时游玩，大约是游玩 6–7h + 吃饭 2h + 移动 1h + 缓冲 1h。亲子、长辈、旺季再放大缓冲比例，先砍锚点不砍缓冲。

## 抵达 / 离开

按实际航班 / 车次压成半天。深夜落地不要排夜游。入境 + 行李 + 去酒店常常 2–3 小时，要算进去。

## 多城市

除非他们坚持，否则 4 天不要排 3 座城；给更紧的主线。
每天最多一次转运。落地晚则第一夜靠近抵达车站/机场。能省回头路时用开口行程（A 进 B 出）。行李方案（存 / 寄 / 少带）写一句。

## 自驾疲劳

车程规则以本节为准。modes.md 只补车型、停车和能源。

| 车程 | 当天怎么排 |
|---|---|
| 约 < 2 小时 | 可当市内移动 |
| 约 2–4 小时 | 算进当天负荷；约 2 小时停一次 |
| 约 4–5 小时 | 轻观光，或当作转运边缘 |
| 约 ≥ 5 小时 | 转运日，不要再塞景区 |
| 约 ≥ 7 小时 | 抵达后不要「顺便逛古城」 |

次日上班 / 上学：最后一段不超过约 5 小时，**或者**在离家 3–5 小时处加一晚缓冲。
过夜点成簇，不要每晚拆包，除非他们要环线。
风景路：早出发、公共观景停车处、非必要不夜开山路。车程长就两人轮开。
进城限行、尾号、预约通行在**排骨架之前**就查（规则见 [china.md](china.md) 的「开车」）；如果限行正好盖住出发或返程时段，改交通方式或改过夜点，不要留到出发前才发现。

## 天气与动态事件

天气是否需要独立成节、预报与历史气候的边界及失败降级见 [live-data.md](live-data.md)（**该文件是天气规则的唯一出处**）。天气独立执行，不阻塞攻略研究；无关天气不扩张检索。

动态现实覆盖静态攻略：台风、停航、临时闭馆、道路管制、大型活动。发现后**重算当天**，不要只加一句「注意可能下雨」。户外日准备室内或低处 Plan B；只有这类真会改变天安排的事件才回到研究的硬缺口里补查，口径见 [research-playbook.md](research-playbook.md)。

## 预算不可行

用户给了数字上限：推荐合计尽量低于上限；更好的放可升级。

硬预算明显不够（例如境外多日、舒适住宿，但总预算只够极端省）：

1. 明确当前目标不可行
2. 给最低仍像旅行的方案
3. 给缩天数 / 换城市 / 淡季选项
4. 不要为了数字去编极限青旅 + 全程免费步行的假行程

## 发出前可行性校验

写完逐日行程后、交付前，把每天按下面五条硬过一遍。这是机械校验，不是「感觉差不多」。

**1. 单日时间对得上**

```
可用时长 = 出门时刻 → 回酒店时刻
当天占用 = 锚点停留合计 + 步行/换乘 + 车程 + 停车找位 + 排队 + 用餐 + 缓冲
要求：当天占用 ≤ 可用时长
```

- 门口到门口不等于游玩时长：10:00–20:00 是 10 小时窗口，不是 10 小时游玩。
- 排队时间只有查到「要排队 / 分时」才计入；没查到就按热门程度给 15–45 分钟。
- 缓冲按 10–15% 留；亲子、长辈、旺季、乐园上调到 20–25%。

**2. 超时就砍锚点，不砍缓冲**

当天占用 > 可用时长时，处理顺序固定：

1. 砍掉最边缘的那个锚点（顺路性最差、可替代性最高的）
2. 把最贵的那个锚点整体挪到别的半天或别的天
3. 缩短用餐为快餐 / 便利店
4. 以上都做完还不够，才直说这一天排不下，给两个减配版本让用户选

**不要**通过压缩缓冲、把「步行 20 分钟」写成「很近」、或假装两个点挨着来消化超时。

**3. 连续高负荷要有缓冲**

- 连续 ≥ 2 天台乐园 / 徒步 / 长途自驾这类「一个主项目即满日」，中间插一个轻日或半天休整。
- 超过 2 天的行程，每天留一段真正的休息（回酒店、咖啡馆坐一小时都算），不能只是「走路慢一点」。
- 抵达日和离开日按半天算，不算完整日。

**4. 时刻类硬约束往前倒推**

末班车、末班船、最晚入园、末班索道、缆车停运时间、日落，属于**不可跨越**的时刻。做法：

- 从硬时刻往前倒推，倒推出「这一项最晚几点必须开始」，写进当天卡片。
- 硬时刻之后的安排一律删掉，不写「如果来得及可以…」。
- 查不到确切时刻的，写「末班时间以官方当日公告为准，建议 X 点前到」并给官网。

**5. 里程 / 车程阈值**

| 判断 | 动作 |
|---|---|
| 单日总里程 > 约 300 km | 当天锚点 ≤ 1，或改成分段过夜 |
| 连续驾驶 > 约 4 小时 | 必须有一个 ≥ 20 分钟的下车休息，写进停靠表 |
| 单日车程 > 约 6 小时 | 当天不再排收费景区 |
| 次日要上班 / 上学 | 最后一段 ≤ 约 5 小时，或在离家 3–5 小时处加缓冲夜 |

没查到实际里程时，用地图量级估算并写明是估算，不要给一个假精确的数字。

## 校验结果怎么用

五条里有任何一条不过，改行程，不要把问题留给用户自己发现。改不动时（例如硬预算 + 硬时刻同时卡死）：

1. 说清哪一条不过、为什么
2. 给 2 个各让一步的方案（缩天数 / 换片区 / 换档位）
3. 不要交一份「看着很满但走不完」的行程
