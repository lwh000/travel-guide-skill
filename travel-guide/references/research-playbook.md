# 检索手册

写酒店、餐厅、景点、价格之前先读。用户只要没有具体推荐的结构大纲时可跳过；大纲里若出现实际目的地、交通或地点建议，仍须核查相关事实。
规划骨架见 [planning.md](planning.md)。**研究档位、常规研究量、来源要求和候选上限以本节为唯一出处**；其他文件只引用，不重复数字。

> **总原则：候选够用就停止扩张，最终写出的硬事实仍须有依据。**
> 完整输出 ≠ 逐个深核所有候选。若关键事实查不到，删去具体断言或调整行程，并给适用的官方核查入口。

## 预订能力、天气与城际票价

先看当前会话实际可用的工具；未使用预订工具就不要声称登录或已代订。不要让用户在聊天中贴密码或验证码。

天气：需要天气信息时跑 `python scripts/live_data.py weather ...`。`TRAVEL_GUIDE_KEYS_FILE` 可指定包外配置；未设置时读取根目录 `local-keys.json`（格式见 `local-keys.example.json`）。数据缺失时只呈现与查询日期对应的结果；不可拿其他日期的气温冒充出行日预报。不要等聊天里再贴 key，也不要把 key 打到对话或 HTML 里。细则见 [live-data.md](live-data.md)。

**天气独立执行，不阻塞主流程**：天气查询和攻略研究是两条线。天气获取失败不触发整份行程重研；天气不影响行程结构时不为它反复搜索。只有脚本结果与目的地、出行日期一致且有来源时才直接使用其 `html`。

飞机 / 高铁 / 火车票价：脚本只给检索骨架，真正数字核对 **12306** / 航司官网或实际可用的官方查询工具后写入表格。一城地铁用官网票价表。高德 JS Key 只有地图权限，不要拿去查公交。

私人本地自驾 HTML 的高德 JS Key 和安全密钥也从配置文件读，按 [maps.md](maps.md) 接 AMap 2.0。分享版或缺任一凭据就不加载 AMap，改路线示意图。飞机 / 高铁 / 火车、一城地铁步行不要地图，列已核实价格或官方查询入口。

本 skill 只为境内及港澳台行程排自驾路线；境外不排自驾路线，也不接境外驾车地图。其余事实仍靠网页搜索 + 打开公开页面 + 可点开的搜索/预订链接。

**时效信息**：余票、可订座位、房价、排队和路况随时变化。能查到时标明查询时间及来源，并给官方复核入口；不能查到时直接给查询入口。参考价格不是报价或库存保证。

## 研究档位（默认 Fast）

输出档（大纲 / 精简 / 完整 / HTML）和研究档是两件事。先按行程复杂度、必核事实数量和用户要求选档；普通短途优先 Fast。研究档控制候选扩张与投入，不能替代最终事实核实。

| 研究档 | 适用情况 | 候选研究参考量（单位） | 常规轮次 | 常规搜索量 | 常规打开量 | 图片搜索 |
|---|---|---|---|---|---|---|
| Fast | 一城短途、关键事实少；普通周末 | 8–10 | 约 2 轮 | 约 3 次 | 约 4 页 | 0–1 次 |
| Standard | 3–5 天、简单多城、多个必订点，或用户要认真比较 | 18–20 | 约 4 轮 | 约 6 次 | 约 7 页 | 0–1 次 |
| Deep | 复杂多城、密集换乘、旺季政策冲突，或用户要求深挖/逐项比较 | 30–35 | 约 6 轮 | 约 10 次 | 约 12 页 | 0–1 次 |

纯结构大纲：可不检索。大纲若推荐实际地点、路线或预订事项，核实支撑这些建议的事实。

表中数字是避免无意义扩张的基线，不是未核实硬事实的豁免。复杂度超过当前档位就升档；最后仍无法核实的数字或规则不写成事实，改给适用的官方核查入口。

- 精简 1–2 天：通常 Fast；必核事项多时升档。
- 完整 3–5 天：通常 Standard；行程很简单时可用 Fast。
- 多城市 / 7 天以上：至少 Standard；换乘和规则复杂时用 Deep。用户只要简要大纲可缩减输出，但已有事实仍需准确。

## Fast 的常规检索节奏

先批量找候选，后定向核关键事实；必要时升档，不为凑数字继续研究：

```
Fast 常规节奏：
- 第 1 轮：约 1–2 次批量搜索，找核心景点、住宿、餐饮和大交通
- 第 2 轮：针对会改变路线或最终声明的事实定向核实
- 结构和最终声明已有可信依据时即停；硬缺口多时升到 Standard
```

- 第 1 轮：一次覆盖核心景点、住宿候选、餐饮候选、必订、大交通；每次调用尽量合并多个 query。天气走 `live_data.py`，不占这一轮。
- 第 1 轮结束**先做停止判断**，把结果分三类：已经能写的、只影响建议可降级的、会改变行程结构必须补查的。
- 第 2 轮：优先补第三类，以及最终要写出的具体价格、开放时间、预约和交通规则。未核实的具体断言删去。
- 不把研究拆成逐酒店 / 逐景点 / 逐餐厅的重复搜索。若硬缺口证明 Fast 不足，改用更合适档位。
- 不得把同一轮拆成逐对象搜索。如果工具一次只能提交一个 query，优先用 1–2 个高覆盖 query，不要按对象串行开轮次。
- Standard / Deep 可以增加轮次（见上表），但每轮仍按类合并。

## 计费

搜索和打开页面分开计，用来衡量候选研究投入：

| 动作 | 单位 |
|---|---|
| 搜索 | 1 |
| 打开网页 | 2 |
| 同一事实跨站交叉验证（第 2 个不同站点） | 3 |
| 图片搜索 | 1 |
| 坐标补查 | 1 |

预算按独立检索动作计：同一次批量搜索中的多个 query 合计 1 次搜索；不得为了把次数压低而假装合并，也不得把一次批量检索拆成逐对象搜索。

开始检索时可内部记 `{档位} used/target`，用于发现研究范围是否该收束或升档，不要展示给用户。`live_data.py`、写 Markdown / HTML、跑 `validate_html.py` 都不计候选研究量。

候选研究量到达参考值后停止扩张候选池。若最终声明仍缺证据，升档定向核实；仍无法核实就删具体断言、给官方入口，不把猜测写成结论。

## 停止扩张候选池

出现下列情况时停止寻找新酒店、餐厅和景点，转入核查与写作：

1. 已找到足够支持最终行程结构的信息（见「信息充分阈值」）
2. 已达到候选数量上限
3. 新搜索只会增加备选细节，不会改变路线或最终声明
4. 当前档位的常规研究量已用完；若仍有硬缺口，先考虑升档或删未核实声明

不要为了让每个备选都更完整而无限细化。主选酒店、核心收费景点、必订点和实际交通的关键事实仍需与最终文案一致。

临近当前档位研究量时停止新候选、图片与可选坐标查询；继续优先核实闭馆、停航、限行、末班车、重大天气等会改变结构的事实。发现来源冲突时仍须核对，或明确写出冲突。

结构性风险仍未核实时，不把高风险路段当已确认；给官方入口并说明哪一天的安排需等核查结果。常规核实顺序：

- 住宿主选 → 核心景点 / 必订事项 → 大交通 → 与行程相关的天气 → 其余删去无证据数字或给官方入口

用户在对话中追加要求（改某天、加某城）时，额度按追加范围单独算，不重算整份。

## 信息充分阈值

下列信息已足以确定行程结构时，停止扩张候选；最终文案中的硬事实继续按来源规则核实：

- 核心目的地
- 核心景点
- 住宿区域
- 主要交通方式
- 必须确认的营业 / 开放信息
- 关键预订入口

剩余细节直接基于已获得信息写作。不要为了填充细节继续研究。查不到的按「数据查不到时怎么写」降级。

## 来源等级

| 级 | 例子 | 能支撑什么 |
|---|---|---|
| S | 政府、景区官网、铁路、航空、使馆、气象台 | 签证、票价、开放时间、交通规则、预警 |
| A | 酒店/餐厅官网、官方旅游局 | 票价、开放时间、店真实存在 |
| B | 高德 / Google Maps / 携程 / 美团 / 大众点评 | 店是否存在、体验、价格带 |
| C | 当地媒体、旅游媒体、博客 | 体验、背景；不单独定票价 |
| D | SEO 聚合、排行榜、搜索摘要 | 只当发现线索 |

票价 / 开放时间：S 或 A。签证：S。店是否存在：A 或 B。用户体验：B 或 C。
**D 级搜索摘要可以发现对象，不能单独证明真实存在。** 高德 / 点评 / 预订平台商家卡（确切店名 + 地址）算 B 级一次确认。

优先官网：文旅局、景区官网、轮渡公司、12306、气象台、市政府停车说明，以及公园、国铁、使馆签证页。然后才是携程 / 美团 / 高德 / 大众点评，或 Google Maps / 官方旅游局。不要把聚合「必去榜」当成开放时间或门票的证据。

## 核查分级：来源要求 ≠ 交叉验证要求

不是每条信息都要 S/A 交叉验证。按这三档花预算，禁止把建议类升级成硬核实。

**S/A 级可靠来源已经满足事实核实要求时，不得为了增加第二个来源而再次搜索或打开网页。来源完整不等于需要交叉验证。** 只有存在冲突、不确定或高风险事实时，才允许再次核验。

### 必须官方核实（S/A，打开 1 个关键页即可）

票价、开放时间、预约、交通规则、签证、天气预警、限行、末班交通。

**同一事实一旦获得可信来源确认，就不得再次搜索、不得打开第二个页面重复确认、不得为了「更保险」重复验证。** 只有发现来源冲突时才允许重新核验。

### 一次确认即可（A 或 B）

酒店是否存在、餐厅是否存在、景点是否存在、停车是否大致存在。

Fast 档：主选酒店和核心收费景点打开 1 页；餐厅和备选酒店用商家卡 / 地图结果里的确切店名即可，不要再开官网 + 地图 + 预订页。

### 不需要额外查

推荐顺序、上午/下午安排、片区组合、吃饭建议、备选逻辑。这些是规划结论，写进行程即可。

## 候选上限：不要为了推荐而搜索

只核实**最终会写入攻略的关键实体**。不要为了凑完整度而增加候选。

| 对象 | 上限 |
|---|---|
| 住宿 | 每城 1 主 + 1 备（备选默认只确认存在 + 价格带） |
| 餐厅 | 每餐最多 1 个主推荐 + 1 个备选；每主片区默认 1 主 + 1 备 |
| 景点 | 只研究最终进入行程的核心景点 |
| 交通 | 只核实真正影响行程结构的交通信息 |

- **完整档只表示最终输出完整**，不代表需要对每个餐厅、景点、酒店、交通节点逐一深度研究。
- 如果用户没有要求大量候选，不得为了丰富内容主动扩展候选池。**已有可用选项时，不得重复搜索更多同类选项。**
- 不要出现「搜 10 家酒店 → 比价格 → 再搜 10 家餐厅 → 再选」这种流程。
- 例外：用户明说「帮我认真选酒店 / 要比一比餐厅」时，住宿最多 3 家、美食清单最多 4 家。

## 防止搜索结果驱动的无限扩展

搜索结果中新发现的地点、餐厅、酒店、活动，**默认不得自动加入研究范围**。只有当它直接解决一个尚未解决的关键需求时，才能进入候选。

不要出现「搜 A → 发现 B → 搜 B → 发现 C → 搜 C」这种链式扩张。

## 冲突

不同页面数字不一致时，按这个顺序取：

1. 最新官方公告
2. 官方网站
3. 官方社交账号 / 小程序
4. 地图 / 预订平台
5. 新闻 / 博客

无法确认时：明确写「不同页面存在差异」并给链接，不要自己猜一个数字。尤其适用于景区、博物馆、轮渡、餐厅、节假日、临时闭馆、天气预警、交通管制。

## 时效

查询日期 ≠ 信息一定有效。尽量按**出行日期**核高时效事实，不要把今天的平日价当成三个月后的节日价。

| 时效 | 事实 | 要求 |
|---|---|---|
| 高 | 票价、开放时间、车次、航班、轮渡、天气、道路限制 | 尽量按出行日期核 |
| 中 | 餐厅营业时间、停车规则、酒店价格 | 写月份/季节带，节假日可能跳价 |
| 低 | 景点介绍、片区特点、旅行建议 | 来源仍要真实 |

## 天气：气候 vs 预报

天气的适用条件、脚本顺序和字段含义以 [live-data.md](live-data.md) 为准，本节只留研究侧规则：

- 天气独立执行，**不阻塞攻略研究**：获取失败不触发整份行程重研，不影响行程结构时不为天气反复搜。
- 需要天气且脚本无有效数据时，可打开官方预报页；仍无与出行日期相符的预报，就明确未取得预报，给查询入口，不补造气温卡片。

## 天气 / 假期 / 时效事实的留痕格式

这类信息查到了也必须让用户看出**你查的是哪一天的数据**，否则一周后跟着走会出事。统一写成：

```
天气：{目的地} {出行日期} 官方预报 XX–XX°C（仅在该日期确有预报时）
      或 {目的地} {月份} 历史气候区间 XX–XX°C（仅在历史数据有来源时；非预报）
      〔来源；查询 YYYY-MM-DD〕
临近预报：{出行前 5 天再核} 台风 / 暴雨以中央气象台及当地气象台为准 ↗链接
```

- 假期：`{年份} 节假日调休` → 写「{节日} 放假 X 天，调休上班日为 …」（来源，查询日期）。没查到当年公告就说「调休以国务院办公厅当年通知为准」并给链接，不要背去年日历。
- 日出日落：只在行程真的绑观景时写，写清日期和地点，不要给一年通用的钟点。
- 每次天气 / 假期事实都必须带查询日期，和其他硬事实一样。

## 数据查不到时怎么写

查不到时先说清已核实部分，再指出尚需官方确认的部分。不要把同类景点、通用营业时间或价格浮动当作目标对象的事实；缺口会改变路线时先定向核查，仍无法确认则调整当天安排。

| 情况 | 这么写 |
|---|---|
| 票价查不到 | 「{景区}出行日票价未核实；以{官方售票入口}为准」，预算中暂列待确认项，不借同类景区价格代填 |
| 票价有两个数 | 「不同页面存在差异（A 页 X 元 / B 页 Y 元），以下单页为准」+ 两个链接，不自己挑一个 |
| 开放时间查不到 | 「{景区}开放时间未核实，暂不把它设为不可替换的当天锚点」+ 官方入口 |
| 酒店价格查不到 | 「{酒店}出行日价格未核实，实时价见{预订页}」；只有实际来源给了区间才写来源、适用日期和区间 |
| 餐厅人均查不到 | 不写该店人均；若需估预算，可另列「餐食预留预算」，写清其估算依据而不冒充商家标价 |
| 餐厅是否还开着 | 「{名称}在{平台}有页面（查询 YYYY-MM-DD）；出行前建议电话确认」 |
| 车次 / 航班 | 「以 12306 / 航司当日查询为准」+ 明确写起始站全名，不给具体班次号 |
| 分时预约是否有票 | 「{渠道}预约，是否还有名额请自行查看」+ 入口链接 |
| 整条检索链路都失败 | 「{项目}未能核实，建议通过{官网/电话}确认」+ 搜索链接 |

原则：

- **能确定的先写**。查不到「确切票价」但查到「旺季约 X 元」就写后者，不要一起丢掉。
- **给的是入口，不是答案**。涉及实时状态的，把官方查询页给全。
- **区分估算和商家事实**。必要的预算预留可估算并注明依据；目标对象的价格、开放时间和政策没有来源就不写数字。
- 未核实的结构性事实较多时，缩小行程范围、升研究档位或让用户先确认关键预订事项；不要靠限制「未确认」出现次数来掩盖缺口。

## 定向打开网页

**搜索结果页已经包含足够可信的信息时，不得打开网页。** 只有下列情况才允许打开：

- 官方页面核实硬事实
- 需要读取具体营业时间 / 票价 / 预约规则
- 搜索摘要不足以支持最终结论

打开页面的常规数量见「研究档位」表。同一对象已有可信来源且没有冲突时，不再打开下一个网页；关键事实与当前档位不匹配时升档或删具体断言。

同一 URL 连续两次读不到就换下家（官网 → 官方社媒 / 小程序 → 地图 → 预订平台），不要刷第三次。全链路都失败才写「未确认」+ 搜索链接。

## 图片来源与搜索

图片搜索是**一次性动作**，只服务于最终输出的视觉素材，见 [media.md](media.md) 的「每城怎么选」。

- 图片搜索只服务于最终输出视觉素材。**不得因为找不到理想图片而反复搜索。**
- Fast 默认 0–1 次图片搜索：只在要 HTML 且尚未进入降级区时，用一次 Commons 批量搜索（封面 + 过夜城，≤6 张，计 1 单位）。
- 已进入降级区或只要对话，不搜图，直接用壳子渐变 / `.art-fig`。

## HTML 不得重新触发研究

写 HTML 只转换已经核实的事实：店名、票价、坐标、天气卡片、导航 URI。

- 不要为 HTML 再搜酒店 / 餐厅 / 景点 / 图片或坐标
- 缺坐标的点不进 `points`，只留正文表格
- HTML 排版本身不新增研究量；若制作时发现原行程关键事实缺证据，按事实核实规则处理或删具体断言
- `validate_html.py` 有 FAIL 时优先修结构、删失效字段、降级展示；只有原行程的关键坐标确实缺失才定向核实，不能为视觉点数扩张研究

## 检索缓存

同一事实记住：对象、内容、来源、查询日期、可信度、适用日期。Markdown、HTML、只改某一天时复用，不要重搜。候选看过但没用的，不要写进正文。

**缓存何时作废（必须重查）**：出行日期改变；价格类事实跨季 / 跨促销期；开放时间随季节切换；用户明说「查最新的」「再确认一下」；来源页面明确更新过；发生台风、闭馆、管制等动态事件。9 月查的旺季价不要在 12 月接着用。

## 什么时候停

满足以下条件之一就停止该类候选检索；最终声明仍按证据要求处理：

1. 已有可靠来源（必须官方核实的达到 S/A，一次确认的达到 A/B）
2. 已满足候选数量
3. 新结果不再产生新信息
4. 剩余信息不会影响行程结构
5. 继续检索明显不值
6. 已达到当前研究档的常规投入；若关键事实仍未核实，升档、调整行程或删具体断言

## 怎么搜

把 `{目的地}` `{片区}` `{月份}` `{年份}` `{出发}` 换成这次的词。

### 住

- `{片区} 酒店 推荐 {月份}`，按需要加上 停车 / 海景 / 亲子 / 近地铁
- `{片区} 民宿` / 境外 `{area} hotel {month}`
- 确认店在对的城镇，不是同名连锁的另一座城
- 用户没说车型时，不要用 SUV 限高或充电桩淘汰酒店

### 吃

- `{片区} 必吃 餐厅 人均` / `{招牌菜} 哪家 本地人`
- `{area} best {cuisine} restaurant reservation`
- Fast 档不逐店核非关键营业细节；若餐厅是当天不可替换的锚点，核实营业日，否则标为可替换建议并给联系入口

### 景

- `{景区} 门票 {年份}` `{景区} 开放时间 周一闭馆 预约`
- 自驾再搜 `{景区} 停车 自驾`
- `{sight} official hours ticket timed entry`

### 走

- `{出发} 到 {目的地} 高铁 时长` 或 `{出发} 自驾 到 {目的地} 公里 小时`，并写出高速名
- `12306 {出发} {到达} 高铁 票价`；机票用航司官网 / 官方渠道
- `{city} 地铁 票价表`（官网，不调高德公交）
- 机场/车站全名（不要送错机场或西站/东站）
- 当天结束得晚会不会错过末班车 / 末班船
- `{city} airport to {area} transit time`

### 什么时候去

- `{目的地} {月份} 天气` / 台风 / 梅雨 / 雪 / 高温（按 [live-data.md](live-data.md) 的天气规则）
- `{年份} 节假日调休` / 当地公共假日 / 学校假期
- 行程绑死观景时再查日出日落

查到后按上面的「留痕格式」写进攻略，带查询日期。

## 什么叫「确认过」

可以写进攻略的店名，必须至少满足「一次确认」：A/B 级结果里出现确切名字。不要编一个听起来很本地的假店名。

| 对象 | Fast（默认） | Standard / Deep |
|---|---|---|
| 主选酒店、核心收费景点、必订 | 打开 1 个官方或商家页 | 打开官方页；票价/开放时间要 S/A |
| 备选酒店、餐厅 | 商家卡 / 地图结果有确切店名 + 价格带 | 用户要认真选时再打开页面 |
| 建议（片区、节奏、备选逻辑） | 不查 | 不查 |

**价格**必须带来源和适用日期。只有来源确有区间才写区间，不套用「节假日翻倍」经验值；官网门票可写查到的数字，并给官方售票入口。

## 深链（安全，不用 API）

中国地图：

- 搜索：`https://www.amap.com/search?query={URL编码的名称}`
- 导航入口：`https://uri.amap.com/search?keyword={URL编码的名称}`
- 驾车（自驾 HTML 才用）：见 [maps.md](maps.md)

携程关键词：`https://you.ctrip.com/search/?keyword={名称}`

美团 / 点评链接经常变；高德链接 +「美团搜店名」就够，不必强行找永久 URL。

境外：

- Google Maps：`https://www.google.com/maps/search/{URL编码的名称}`
- 有官网预订或旅游局页面就用官网

轮渡和分时票：官网或官网上写的微信小程序，并写「实名分时」。

链接新标签打开。按钮文字用地名，不要「点击这里」。
